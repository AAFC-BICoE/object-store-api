= Object Storage

== Storage

The Object Store module stores files using the implementation set by `dina.fileStorage.implementation` (see Configuration):

 * `FS`: files are stored on the file system, under `dina.fileStorage.root`
 * `S3`: files are stored in an S3-compatible object storage using https://opendal.apache.org/[Apache OpenDAL]

In both cases, files are stored per bucket as `<bucket>/<ab>/<cd>/<fileIdentifier><extension>`, where `<ab>` and `<cd>` are the first 4 characters of the `fileIdentifier`. Derivatives are stored under `<bucket>/derivatives/`.

MinIO is no longer used. Files stored by MinIO in its internal format (folders containing `xl.meta` files) can't be read by the `FS` implementation. In `FS` mode, the storage root is checked at startup, before the API accepts requests, and the application will not start if `xl.meta` files are found. Once a check completes, it is not run again. Paths that can't be read are skipped and reported in the logs, and the check runs again on the next startup.

To check an existing storage root before upgrading: `find <root> -name xl.meta -print -quit`.

== Object Metadata

The Object Store workflow consists of the upload of an object (a file) and the submission of the associated metadata. Some data available at the upload stage should be preserved and transferred to the associated metadata once the latter is submitted. For example: the original filename, the hash of the file, the received media type, the detected media type, etc.

== Expected Sequence

 * Multipart upload of a file in a specific bucket
 * The backend returns a uuid representing the `fileIdentifier`
 * Post of the metadata with `fileIdentifier` set to the uuid return be the previous step
 * The file is available for download using the bucket and the `fileIdentifier`
